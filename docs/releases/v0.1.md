# Supremely v0.1

**The first usable release of Supremely.**

v0.1 establishes a coherent, installable version of Supremely that can be self-hosted, used by real communities, and evaluated through actual use.

The goal is not feature completeness or API stability. The goal is a solid foundation we can ship, use, learn from, and iterate on toward v0.2.

## Release principles

- A new user should be able to install and understand Supremely without knowing its internals.
- The core product should work end-to-end rather than exist as disconnected features.
- Self-hosting is a first-class use case.
- SQLite should provide the simplest path to getting started; PostgreSQL should be supported for production use.
- Email should remain optional infrastructure.
- Tenant isolation, permissions, security, and data integrity are release requirements.
- Documentation is part of the product.
- v0.1 may change significantly after release. Compatibility guarantees begin later.

## Scope

### 1. Installation and first-run setup

Establish a reliable path from a clean machine to a functioning Supremely installation.

- [ ] Docker Compose works from a clean machine
- [ ] First-run setup wizard
- [ ] SQLite default
- [ ] PostgreSQL option
- [ ] Platform Admin creation
- [ ] Optional email configuration
- [ ] First Organization creation
- [ ] Setup can recover safely from interruption or configuration errors

**Done when:** a new user can install Supremely, complete setup, and reach a functioning Organization without manually modifying the database or application internals.

### 2. Organizations and tenancy

Make the Organization the fundamental tenant and community boundary.

- [ ] Create and configure an Organization
- [ ] Organization membership
- [ ] Users can belong to multiple Organizations
- [ ] Organization switching/selection
- [ ] Tenant-scoped data access
- [ ] Tenant isolation tests

**Done when:** multiple Organizations can safely coexist in one Supremely installation without data or permission leakage between them.

### 3. Authentication, users, and permissions

Provide the identity and authorization foundation for the platform.

- [ ] Member authentication
- [ ] Platform Admin authentication
- [ ] Installation-level and Organization-level roles
- [ ] Permission enforcement
- [ ] Account/recovery path that does not require configured email
- [ ] Authentication and authorization tests

**Done when:** users can authenticate reliably and every protected operation is governed by explicit, tested permissions.

### 4. Core content model

Provide the publishing foundation shared by Supremely's content experiences.

- [ ] Pages
- [ ] Posts / typed structured content
- [ ] Draft and published states
- [ ] Public/private visibility
- [ ] Organization-scoped content
- [ ] Basic content authoring and management

**Done when:** an Organization can create, manage, publish, and control access to its core content.

### 5. Discussions

Provide a durable community discussion experience distinct from real-time chat.

- [ ] Discussion areas/groups
- [ ] Topics
- [ ] Replies
- [ ] Authors and timestamps
- [ ] Public/private access rules
- [ ] Permission-aware moderation basics

**Done when:** members can participate in persistent, readable discussions with correct visibility and permissions.

### 6. Themes and presentation

Establish a clear separation between content and presentation and make themes a supported extension surface.

- [ ] Theme loading and selection
- [ ] Default theme
- [ ] Example/reference theme
- [ ] Theme contract documented
- [ ] Public content can be presented through themes
- [ ] Theme failures degrade safely

**Done when:** a developer can understand the theme system from the documentation and build or modify a theme without reverse-engineering Supremely internals.

### 7. Newsletter and audience foundation

Establish the first useful newsletter/audience capability without making email mandatory for the platform itself.

- [ ] Organization audience/subscriber model
- [ ] Subscriber management
- [ ] Email provider configuration
- [ ] Basic newsletter creation/sending path when email is configured
- [ ] Graceful operation when email is not configured

**Done when:** an Organization with email configured can maintain an audience and send a basic newsletter, while installations without email remain fully usable for non-email features.

### 8. Administration

Provide the controls necessary to operate an installation and its Organizations.

- [ ] Platform Admin area
- [ ] Organization management
- [ ] User/member management
- [ ] Essential installation configuration
- [ ] Organization administration
- [ ] Clear separation between platform and Organization administration

**Done when:** normal operational tasks can be performed through Supremely rather than direct database or server intervention.

### 9. Background jobs

Provide a dependable foundation for asynchronous work.

- [ ] Background worker execution
- [ ] Job persistence/queue behavior
- [ ] Failure handling
- [ ] Retry behavior where appropriate
- [ ] Operational visibility sufficient to diagnose failures

**Done when:** asynchronous work required by v0.1 can run reliably and failures can be understood and recovered from.

### 10. Production deployment

Make self-hosting realistic beyond local development.

- [ ] Production-oriented Docker deployment documented
- [ ] Persistent storage documented
- [ ] Environment/configuration reference
- [ ] PostgreSQL production path
- [ ] Reverse proxy and HTTPS guidance
- [ ] Upgrade/restart guidance
- [ ] Backup considerations documented

**Done when:** a technically competent user can deploy Supremely on a server using the project's documentation without having to infer undocumented production requirements.

### 11. Security baseline

Treat security as part of the release rather than post-release cleanup.

- [ ] Authorization review
- [ ] Tenant isolation review
- [ ] CSRF protection
- [ ] Secure session/cookie defaults
- [ ] Input/output safety review
- [ ] Secret/configuration handling review
- [ ] Dependency/security scanning
- [ ] Vulnerability reporting process documented

**Done when:** the core v0.1 attack surfaces have been deliberately reviewed and critical security assumptions are covered by tests or documented controls.

### 12. Tests and continuous integration

Create enough automated confidence to ship and accept contributions responsibly.

- [ ] CI runs on relevant changes/PRs
- [ ] Core application test suite
- [ ] Authentication/authorization coverage
- [ ] Tenant isolation coverage
- [ ] Installation/setup smoke coverage
- [ ] Database migration coverage
- [ ] CI must be green for a release

**Done when:** regressions in the core v0.1 experience are likely to be caught before release.

### 13. Contributor experience

Make the repository understandable and approachable to people who did not build it.

- [ ] CONTRIBUTING.md is current
- [ ] Local development setup is documented
- [ ] Architecture entry point is clear
- [ ] Bug report issue form/template
- [ ] Feature request issue form/template
- [ ] Pull request template
- [ ] Labels and milestones established
- [ ] `good first issue` and `help wanted` used intentionally

**Done when:** an external developer can understand the project, run it locally, find useful work, and submit a contribution without private guidance from the maintainers.

### 14. v0.1 documentation

Document the product people are actually receiving.

- [ ] Installation guide
- [ ] Configuration reference
- [ ] Production deployment guide
- [ ] Architecture overview
- [ ] Theme documentation
- [ ] Plugin/extension documentation appropriate to implemented v0.1 capabilities
- [ ] Upgrade guidance
- [ ] Known limitations

**Done when:** the documentation accurately describes v0.1 and does not depend on tribal knowledge.

### 15. v0.1 release

Package the work as Supremely's first public usable release.

- [ ] v0.1 scope reviewed and complete enough to ship
- [ ] All release-blocking bugs resolved
- [ ] CI green
- [ ] Documentation reviewed against the actual product
- [ ] CHANGELOG updated
- [ ] Known limitations documented
- [ ] Version set to `0.1.0`
- [ ] Git tag `v0.1.0`
- [ ] GitHub Release published
- [ ] Clean-install smoke test performed against the release

**Done when:** `v0.1.0` is a reproducible, documented release that someone outside the core team can install and use.

## Explicitly not required for v0.1

v0.1 is a foundation, not a completeness milestone. Features should not be added merely because they may eventually belong in Supremely.

Unless required to make the core v0.1 experience coherent, the following can wait for later releases:

- Broad third-party integration ecosystem
- Mature plugin marketplace/distribution
- Large theme ecosystem
- Migration tooling from other community/publishing platforms
- Enterprise administration features
- Extensive analytics
- Full API stability guarantees
- Backward compatibility guarantees for extension interfaces
- Every envisioned vertical content type or workflow

## Release tracking

This document defines the intended scope of v0.1. Execution is tracked in the GitHub **v0.1 milestone** and its associated issues.

As implementation teaches us more, this document may change. Changes should reflect deliberate product decisions rather than silently expanding the release.

After v0.1 ships, actual usage and feedback should determine the scope of v0.2.
