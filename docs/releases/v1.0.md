# Supremely v1.0

**The first usable release of Supremely.**

v1.0 establishes a coherent, installable version of Supremely that can be self-hosted, used by real communities, and evaluated through actual use.

The goal is not feature completeness or API stability. The goal is a solid foundation we can ship, use, learn from, and iterate on after release.

## Release principles

- A new user should be able to install and understand Supremely without knowing its internals.
- The core product should work end-to-end rather than exist as disconnected features.
- Self-hosting is a first-class use case.
- SQLite should provide the simplest path to getting started; PostgreSQL should be supported for production use.
- Email should remain optional infrastructure.
- Tenant isolation, permissions, security, and data integrity are release requirements.
- Documentation is part of the product.
- Releases follow semantic versioning. v1.0 may still change significantly after release; breaking changes after v1.0.0 are signaled by the version number.

## Where the product deviates from this plan

Two items shipped deliberately differently from the way this document describes
them. Both are recorded here rather than quietly ticked.

**The database engine is not a setup question.** Section 1 lists "PostgreSQL
option" alongside the wizard steps, which reads as a choice the operator makes
during setup. It is resolved by configuration instead: `DATABASE_URL` is read
before the application starts, and the wizard runs against whatever it finds.
The wizard does not own a decision that has to survive a container restart.

**Email is absent from setup, not optional within it.** Section 1 lists
"Optional email configuration", which reads as a step you may skip. There is no
email step at all. A provider is configured after install at
`/admin/settings`, with a test send. Nothing in installing, publishing or
onboarding touches email, so there was nothing to make optional.

## Explicitly not required for v1.0

v1.0 is a foundation, not a completeness milestone. Features should not be added merely because they may eventually belong in Supremely.

Unless required to make the core v1.0 experience coherent, the following can wait for later releases:

- Broad third-party integration ecosystem
- Mature plugin marketplace/distribution
- Large theme ecosystem
- Migration tooling from other community/publishing platforms
- Enterprise administration features
- Extensive analytics
- Full API stability guarantees
- Backward compatibility guarantees for extension interfaces
- Every envisioned vertical content type or workflow

## Release tracking

This document defines the intended scope of v1.0. Execution is tracked in the GitHub **v1.0.0 milestone** and its associated issues.

As implementation teaches us more, this document may change. Changes should reflect deliberate product decisions rather than silently expanding the release, and a deviation gets written down (see "Where the product deviates from this plan") rather than absorbed into a ticked box.

After v1.0.0 ships, actual usage and feedback should determine what comes next.
