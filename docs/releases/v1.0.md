# Supremely v1.0

**The first usable release of Supremely.**

v1.0 establishes a coherent, installable version of Supremely that can be self-hosted, used by real communities, and evaluated through actual use.

The goal is not feature completeness or API stability. The goal is a solid foundation we can ship, use, learn from, and iterate on after release.

## Release principles

- A new user should be able to install and understand Supremely without knowing its internals.
- The core product should work end-to-end rather than exist as disconnected features.
- Self-hosting is a first-class use case.
- SQLite should provide the simplest path to getting started; PostgreSQL should be supported for production use.
- Email should remain optional infrastructure.
- Tenant isolation, permissions, security, and data integrity are release requirements.
- Documentation is part of the product.
- Releases follow semantic versioning. v1.0 may still change significantly after release; breaking changes after v1.0.0 are signaled by the version number.

## The four components

v1.0 is presented to users as four things. Each maps onto the numbered scope
sections below; this table is the summary for someone who does not want to read
the checklist. "Custom content" is the one piece deliberately held for v2.0.

| Component | Promise | Where it stands on `main` |
|---|---|---|
| **CMS (publishing)** | Pages | Done. `page` is a core content type with draft/published states, public or members-only visibility, and a choice of site or community presentation (section 4). |
| | Posts | Done. `article` is the core post type, with `event` and the content-library types (announcement, episode, recording, resource, team member) alongside it. A run of fixes from real use is open (#78, #80 to #84). |
| | Custom content | **v2.0.** Types are registered in code today, by core or by a plugin. An organization defining its own type from the console, without code, is the v2.0 item (see the roadmap). |
| **Discussions (forum)** | Basic threading | Done. Groups hold topics; a reply may answer the topic or one other reply, one level deep (section 5). |
| | Replies | Done. Authors edit and delete their own; timestamps and reply counts are kept. |
| | Reactions | Done. Three reactions (👍 ❤️ 🎉) on topics and replies, one per person per item. |
| | Moderation | Done. Lock, pin, hide and delete on topics and replies; members flag content and moderators work a queue at `/manage/flags`. |
| **Newsletters** | Mailgun integration | **Open, no issue yet.** Mailgun's SMTP relay works through the existing provider; a first-class Mailgun setup (API key, domain, test send) does not exist. |
| | Gmail SMTP integration | Works through the generic SMTP provider (STARTTLS, port 587, an app password). Not documented as a recipe; that is the open half (section 7). |
| **Membership** | Tiers (Free and Private) | **Open (#85).** Membership is a role today, and content visibility is public or members-only. Tiers extend both. Payment for a tier is a separate decision (#86, see below). |

### Decisions for the release review

These are the questions this document cannot settle by itself.

1. **Stripe (#86) in v1.0 or v2.0?** The promise is "create tiers (Free and
   Private)", which #85 delivers without payments. Stripe is a large,
   externally dependent piece with webhooks to keep in sync. Recommendation:
   move #86 to v2.0 and ship tiers where a Private tier is granted by an
   admin.
2. **Direct audio/video upload (#84) in v1.0 or v2.0?** It needs new size
   limits, range-request serving and storage thinking, none of which the image
   pipeline has. Recommendation: move to v2.0; #83 (render the video that is
   already linked) is the v1.0 fix.
3. **Mailgun: SMTP relay or API?** The relay needs only documentation. The
   API needs a second provider behind the mailer. Recommendation: document the
   relay for v1.0 and file the API provider as a v1.0 issue only if the team
   wants Mailgun in the settings screen by name.
4. **Version number.** `pyproject.toml` and the CHANGELOG both say `0.1.0`
   while this plan and the milestone say `1.0.0`. One of them has to move
   before #70.

## Where the product deviates from this plan

Two items shipped deliberately differently from the way this document describes
them. Both are recorded here rather than quietly ticked.

**The database engine is not a setup question.** Section 1 lists "PostgreSQL
option" alongside the wizard steps, which reads as a choice the operator makes
during setup. It is resolved by configuration instead: `DATABASE_URL` is read
before the application starts, and the wizard runs against whatever it finds.
The wizard does not own a decision that has to survive a container restart.

**Email is absent from setup, not optional within it.** Section 1 lists
"Optional email configuration", which reads as a step you may skip. There is no
email step at all. A provider is configured after install at
`/admin/settings`, with a test send. Nothing in installing, publishing or
onboarding touches email, so there was nothing to make optional.

## Explicitly not required for v1.0

v1.0 is a foundation, not a completeness milestone. Features should not be added merely because they may eventually belong in Supremely.

Unless required to make the core v1.0 experience coherent, the following can wait for later releases:

- Broad third-party integration ecosystem
- Mature plugin marketplace/distribution
- Large theme ecosystem
- Migration tooling from other community/publishing platforms
- Enterprise administration features
- Extensive analytics
- Full API stability guarantees
- Backward compatibility guarantees for extension interfaces
- Every envisioned vertical content type or workflow
- Organization-defined custom content types without code (v2.0; types are registered in code or by a plugin in v1.0)
- Importing content from WordPress, Ghost, Discourse and similar (#79, v2.0)
- Payments and paid tiers, if the review moves #86 to v2.0
- Direct audio and video file hosting, if the review moves #84 to v2.0

## Release tracking

This document defines the intended scope of v1.0. Execution is tracked in the GitHub **v1.0.0 milestone** and its associated issues.

As implementation teaches us more, this document may change. Changes should reflect deliberate product decisions rather than silently expanding the release, and a deviation gets written down (see "Where the product deviates from this plan") rather than absorbed into a ticked box.

After v1.0.0 ships, actual usage and feedback should determine what comes next.
