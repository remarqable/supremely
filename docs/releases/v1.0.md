# Supremely v1.0

**The first usable release of Supremely.**

v1.0 establishes a coherent, installable version of Supremely that can be
self-hosted, used by real communities, and evaluated through actual use.

The goal is not feature completeness or API stability. The goal is a solid
foundation we can ship, use, learn from, and iterate on after release.

## Release principles

- A new user should be able to install and understand Supremely without knowing its internals.
- The core product should work end-to-end rather than exist as disconnected features.
- Self-hosting is a first-class use case.
- SQLite is the simplest path to getting started; PostgreSQL is supported for production use.
- Email is optional infrastructure. Installing, publishing and onboarding never require it.
- Tenant isolation, permissions, security, and data integrity are release requirements.
- Documentation is part of the product.
- Releases follow semantic versioning. v1.0 may still change significantly after release; breaking changes after v1.0.0 are signaled by the version number.

## The four components

v1.0 is presented to users as four things. Each maps onto the numbered scope
sections below; this table is the summary for someone who does not want to
read the tables.

| Component | Promise | Where it stands |
|---|---|---|
| **CMS (publishing)** | Pages | Done. `page` is a core content type with draft/published states, public or members-only visibility, and a choice of site or community presentation (section 4). |
| | Posts | Done. `article` is the core post type, with `event` and the content-library types (announcement, episode, video, resource, team member) alongside it. Editor and Videos fixes from real use are open (section 4). |
| | Custom content | **v2.0.** Types are registered in code today, by core or by a plugin. An organization defining its own type from the console, without code, is a v2.0 item. |
| **Discussions (forum)** | Basic threading | Done. Groups hold topics; a reply may answer the topic or one other reply, one level deep (section 5). |
| | Replies | Done. Authors edit and delete their own; timestamps and reply counts are kept. |
| | Reactions | Done. Three reactions (👍 ❤️ 🎉) on topics and replies, one per person per item (#106). |
| | Moderation | Done. Lock, pin, hide and delete on topics and replies; members flag content and moderators work a queue at `/manage/flags`. |
| **Newsletters** | Mailgun integration | **Open (#104).** Mailgun's SMTP relay works through the generic provider today; nothing names Mailgun. The shape of the integration is an open question (see below). |
| | Gmail SMTP integration | Works through the generic SMTP provider with an app password. The step-by-step recipe is **open (#105)**. |
| **Membership** | Tiers (Free and Private) | **Open (#85).** Membership is a role today, and content visibility is public or members-only. Tiers extend both. Paying for a tier through Stripe is v2.0 (#86). |

## Decisions made in the release review

Recorded here so the tables below can be read without the history.

| Decision | Outcome |
|---|---|
| Stripe payments for paid tiers (#86) | **v2.0.** Tiers ship in v1.0 with a Private tier granted by an admin (#85). |
| Direct audio and video file upload (#84) | **v2.0.** Rendering the video that is already linked (#83) is the v1.0 fix. |
| Database engine | **Not a setup question.** `DATABASE_URL` is read before the application starts and the wizard runs against whatever it finds. The plan no longer lists it as a wizard step. |
| Email configuration | **Not a wizard step.** Setup completes with no provider; a provider is configured afterwards in settings, with a test send. The plan no longer lists it as a wizard step. |
| Mailgun and Gmail | **v1.0.** Both are tracked as issues (#104, #105). |

## Explicitly not required for v1.0

v1.0 is a foundation, not a completeness milestone. Features should not be
added merely because they may eventually belong in Supremely. Unless required
to make the core v1.0 experience coherent, the following can wait.

| Item | Where it stands |
|---|---|
| Organization-defined custom content types without code | v2.0. Types are registered in code or by a plugin in v1.0. |
| Importing content from WordPress, Ghost, Discourse and similar | v2.0 (#79). |
| Payments and paid tiers through Stripe | v2.0 (#86). |
| Direct audio and video file hosting | v2.0 (#84). |

## Release tracking

This document defines the intended scope of v1.0. Execution is tracked in the
GitHub **v1.0** milestone and its issues.

As implementation teaches us more, this document may change. Changes should
reflect deliberate product decisions rather than silently expanding the
release, and a deviation gets written down in the decisions table rather than
absorbed into a Done row.

After v1.0.0 ships, actual usage and feedback should determine what comes next.
